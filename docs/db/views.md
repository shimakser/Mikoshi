# Views

## Regular Views (Обычные представления)

Обычная View — это сохраненный SQL-запрос (виртуальная таблица). База данных не хранит результаты этого запроса на диске. Каждый раз, когда вы делаете `SELECT * FROM my_view`, планировщик запросов БД подставляет текст запроса из View в ваш вызов и выполняет его на лету.

### Use Cases (Когда использовать)

- **Инкапсуляция и переиспользование:** Скрытие сложных JOIN, фильтраций и агрегаций от конечного приложения. Разработчик просто делает SELECT, не задумываясь о том, что под капотом объединяются 5 таблиц.
- **Безопасность (Security/Masking):** Ограничение доступа к строкам или колонкам. Например, можно создать View, которая показывает зарплаты только публичных должностей, и дать пользователю права на чтение только этой View, а не исходной таблицы.
- **Адаптация схемы (Legacy):** Если структура исходной таблицы изменилась, но старым приложениям нужен старый формат, View может выступать как адаптер (маппинг старых колонок на новые).

## Materialized Views (Материализованные представления)

В отличие от обычных View, Materialized View (MatView) сохраняет результат запроса на диск в виде реальной физической таблицы.

### Когда предпочесть обычной View

- _Тяжелые аналитические запросы:_ Если запрос агрегирует миллионы строк, делает сложные математические вычисления или собирает данные из десятка таблиц, выполнение обычной View каждый раз будет "убивать" CPU базы данных и занимать секунды/минуты.
- _Толерантность к задержкам (Eventual Consistency):_ MatView идеально подходит, если приложению не нужны данные в реальном времени. Например: отчет по продажам за прошлый день, дашборд аналитики, который достаточно обновлять раз в час, или предварительно рассчитанные рекомендации.

### Refreshing

Поскольку данные лежат на диске, они устаревают при изменении базовых таблиц. Их нужно обновлять вручную (или по крону/триггеру).

1. Базовый `REFRESH MATERIALIZED VIEW`
    - _Как работает:_ БД заново выполняет исходный запрос, полностью очищает старые данные MatView и записывает новые.
    - _Проблема (Блокировка):_ Во время этой операции PostgreSQL берет эксклюзивную блокировку (ACCESS EXCLUSIVE). Это значит, что пока идет рефреш (а он может идти долго), любые попытки прочитать данные из MatView (SELECT) будут заблокированы. Для production-дашбордов это часто неприемлемо.
2. Опция `CONCURRENTLY`
    - _Как работает:_ `REFRESH MATERIALIZED VIEW CONCURRENTLY my_view;`
        PostgreSQL создает новую скрытую временную таблицу с новыми данными, затем сравнивает её со старыми данными (вычисляет diff) и применяет только INSERT, UPDATE и DELETE к существующей MatView.
    - _Преимущество:_ Эта операция не блокирует параллельные SELECT запросы. Приложение продолжает читать старые данные, пока новые не будут готовы.
    - _Жесткое требование:_ Для работы CONCURRENTLY на материализованном представлении обязательно должен быть создан уникальный индекс (UNIQUE INDEX) хотя бы по одной колонке (чтобы Postgres понимал, какие именно строки изменились и мог сопоставить старую и новую версию).

---

## Итог

Используйте Regular Views для абстракции логики и секьюрности, если underlying-запросы быстрые. Используйте Materialized Views, когда нужно закэшировать очень тяжелую аналитику, и бизнес готов мириться с тем, что данные отстают на X минут/часов.
