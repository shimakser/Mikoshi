# DynamoDB

## Partition Key и Sort Key

**Partition Key (PK)** — ключ, определяющий, в какой физический shard (partition) DynamoDB поместит данные.

**Sort Key (SK)** — вторичный ключ внутри одной partition, определяющий порядок элементов.

Как это влияет на производительность
1. PK управляет распределением нагрузки.<br>
    Если PK «горячий» (мало уникальных значений, все запросы идут в одну partition) → происходит throttling.
    Хороший PK = высокая кардинальность и равномерное распределение.
2. PK + SK позволяют эффективно выбирать диапазоны данных.<br>
   Query может выполнить:<br>
       - PK = ?<br>
       - SK BETWEEN ? AND ?<br>
       - SK > ?, SK < ?, begins_with(SK)<br>
   Это быстрые операции O(1) для поиска по PK и O(log n / O(n)) внутри partition.
3. Отсутствие SK → таблица с простым ключом (только PK).<br>
   Можно получить лишь 1 item по PK.<br>
   Нельзя эффективно делать range queries.

## Разница между Scan и Query

### Query

Поиск по фиксированному PK + опциональные условия по SK.

_Характеристики:_
* быстрый
* читает только нужную partition
* может использовать индекс (GSI/LSI)
* фильтры применяются после отбора, но только по запрошенной части

Типичное использование:

    WHERE PK = X AND SK BETWEEN A AND B

### Scan

Полный перебор всей таблицы.

_Характеристики:_
* медленный
* читает весь volume таблицы
* сканирует все partitions
* дорогая операция по RCU
* используется только если нет ключевых условий

### Итого
Query — правильный способ получать данные.

Scan — крайняя мера.

## Global Secondary Index (GSI) and Local Secondary Index (LSI)

### Local Secondary Index (LSI)

* Тот же PK, что и у основной таблицы
* Новый Sort Key
* Создаётся ТОЛЬКО при создании таблицы
* Хранится в тех же partition
* Размер ограничен лимитом 10 ГБ на partition
* Используется для альтернативной сортировки внутри одного PK.

### Global Secondary Index (GSI)

* Имеет свой собственный PK и SK
* Можно создать/удалить в любое время
* Хранится в других partition
* Имеет собственные RCU/WCU
* Позволяет запрашивать данные по другой модели доступа
* Используется для совершенно других запросов, чем основная таблица.

### Короткая разница

| Свойство        | LSI                         | GSI                          |
| --------------- | --------------------------- | ---------------------------- |
| PK              | тот же                      | свой                         |
| SK              | другой                      | другой                       |
| Момент создания | только при создании таблицы | в любое время                |
| Хранение        | та же partition             | независимые partitions       |
| Лимит           | общий 10 GB                 | нет ограничения на partition |
| Нагрузка        | общая с таблицей            | отдельная                    |

## DynamoDB Streams

Это поток изменений таблицы: каждый insert/update/delete создаёт элемент события (строка до/после).

Streams — это аналог Change Data Capture.

_Что содержится в событии:_
* OldImage (до изменения)
* NewImage (после изменения)
* тип операции: INSERT / MODIFY / REMOVE
* время
* ключи элемента

_Практические кейсы:_
1. Реализация event-driven архитектуры<br>
    Таблица → Stream → Lambda → обработка.
2. Синхронизация данных между таблицами<br>
    Например: денормализация данных или поддержание materialized views.
3. Аудит изменений<br>
   Запись изменений в S3 или Elasticsearch.
4. Кеш-инвалидация<br>
   Обновление Redis при изменении данных в DynamoDB.
5. Репликация между регионами<br>
   Применение изменений в другой таблице в другом регионе.
6. Реакция на бизнес-события<br>
   _Пример:_ при создании заказа — отправить email.
