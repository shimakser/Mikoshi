# OAuth2

**Аутентификация** — процедура проверки подлинности, например проверка подлинности пользователя путем сравнения введенного им пароля с паролем, сохраненным в базе данных.
**Авторизация** — предоставление определенному лицу или группе лиц прав на выполнение определенных действий.

**OAuth2** — протокол авторизации, позволяющий выдать одному сервису (приложению) права на доступ к ресурсам пользователя на другом сервисе. Протокол избавляет от необходимости доверять приложению логин и пароль, а также позволяет выдавать ограниченный набор прав, а не все сразу.

Результатом авторизации является access token.
В протоколе описано несколько вариантов авторизации, подходящих для различных ситуаций:
- авторизация для приложений, имеющих серверную часть (чаще всего, это сайты и веб-приложения).
- авторизация для полностью клиентских приложений (мобильные и desktop-приложения).
- авторизация по логину и паролю.
- восстановление предыдущей. авторизации.

## OAuth2 Flows

### Authorization Code

1. Клиент посылает запрос на авторизацию с сервера передавая ID и секрет; он также предоставляет области действия и URI конечной точки (URI перенаправления) для отправки токена или авторизационного кода.
2. Сервер авторизации аутентифицирует Клиента, а также проверяет, разрешены ли запрошенные области.
3. Владелец ресурса взаимодействует с сервером для предоставления доступа.
4. Сервер авторизации перенаправляет обратно код или токен, в зависимости от типа предоставления. Также может быть возвращен Refresh Token.
5. С токеном клиент запрашивает доступ к ресурсу с сервера ресурсов.


### Authorization Code flow + PKCE (Proof Key for Code Exchange)

**Проблема:** Классический Authorization Code требовал client_secret (пароль самого приложения) для обмена кода на токен. В мобильных приложениях и SPA скомпилированный код можно декомпилировать и украсть этот секрет (они называются Public Clients).

**Решение PKCE:** Динамический секрет, генерируемый на лету для каждой транзакции.
1. Клиент генерирует случайную строку (`code_verifier`) и хеширует ее (`code_challenge = SHA256(verifier)`).
2. Клиент перенаправляет пользователя на Auth Server, передавая `code_challenge`.
3. Пользователь вводит логин/пароль. Auth Server запоминает `code_challenge` и возвращает `authorization_code`.
4. Клиент делает POST-запрос за токеном, передавая `authorization_code` и оригинальный `code_verifier`.
5. Auth Server сам хеширует `code_verifier` и сравнивает с сохраненным `code_challenge`. Если совпало — токен выдан. Перехват кода злоумышленником ничего не даст, так как у него нет `code_verifier`.

### Client Credentials flow

Используется исключительно для взаимодействия машина-машина (M2M), когда нет пользователя.
- _Как работает:_ Сервис А отправляет свои client_id и client_secret на Auth Server и сразу получает Access Token.
- _Особенность:_ Здесь нет понятия Refresh Token, так как сервис всегда может запросить новый Access Token по своим статичным учетным данным.

### Device Flow

Разработан для устройств без удобного ввода (Smart TV, консоли, CLI-утилиты).

- _Как работает:_ Телевизор запрашивает у Auth Server код (например, ABCD-1234) и показывает его на экране с просьбой зайти на условный google.com/device с телефона.
- _Под капотом:_ Телевизор начинает поллить (polling) Auth Server (делать запросы каждые 5 секунд): "Пользователь уже ввел код?". Как только пользователь на телефоне вводит код и авторизуется, очередной поллинг от телевизора завершается успешно, и он получает токены.
