# Distributed Coordination

Это совокупность механизмов и протоколов, которые позволяют нескольким узлам распределённой системы согласованно принимать решения, 
синхронизировать состояние и обеспечивать корректную работу при сбоях, сетевых задержках и разделениях сети.

---

## Проблемы, которые решает

### Согласованное изменение общего состояния

Когда несколько узлов читают/пишут одну и ту же сущность (например offset, конфиг, shard assignment), система должна гарантировать корректный порядок изменений.

### Обеспечение единственного лидера

Многие системы требуют единственного ведущего узла, чтобы избегать split-brain.

### Управление жизненным циклом задач

- Кто будет обрабатывать shard?
- Что происходит при падении узла?
- Как переназначить работу?

### Гарантия, что операции выполняются ровно один раз

Обычно достигается через fencing tokens + версии узла + monotonic counters.

### Synchronization & locking

Распределённые блокировки, барьеры, очереди, семафоры.

## Leader Election

_Коротко:_ выбрать один узел, который будет координатором для операций, чтобы избежать гонок и дублирующей работы.

### Жизненный цикл 

1. Все узлы стартуют как кандидаты/фолловеры.
2. Если никто не лидер, узел пытается стать лидером (создаёт znode или инициирует голосование).
3. Узел, который получает majority голосов (Raft) или минимальный seq-id (ZK), становится лидером.
4. Лидер посылает heartbeats; если heartbeats прекращаются → происходит новый раунд выборов.
5. При смене лидера применяют fencing token/epoch, чтобы старый лидер не продолжил работу.

_Простая аналогия:_ круг студентов — тот, у кого есть флаг, отвечает; если студент упал — флаг переход к следующему по правилам.

### Модели реализации

#### Zookeeper Ephemeral Sequential Nodes

Используется в Kafka (до KRaft), HBase, Hadoop.

_Алгоритм:_
1. каждый узел создаёт /election/node_ с sequential id
2. узел с минимальным id = лидер
3. остальные наблюдают (watch) следующего перед собой
4. если лидер умирает → ephemeral node исчезает → выборы

_Свойства:_
* strong consistency store
* мгновенное обнаружение падения
* нет split-brain (при корректно настроенных таймаутах)
* fencing token можно реализовать через version

#### Raft Leader Election

Используется в etcd, Consul, KRaft (Kafka без ZK).

_Ключевые элементы:_
* randomized election timeout
* term (эпоха) — monotonically increasing
* follower → candidate → leader
* majority quorum → победитель

_Почему работает стабильно:_
* случайный timeout уменьшает вероятность конфликтов
* quorum гарантирует согласованность commit log

#### Lease-based Leader Election

Используется в Hazelcast, Redis Redlock, Dynamo.

_Идея:_
* узел получает lease на N ms
* продлевает lease (renewal)
* если lease истёк → лидерство переходит другому

_Проблема_ — clock skew.
_Решение_ — fencing tokens.

## Consensus

_Коротко:_ множество узлов должны согласиться на одну версию правды (например: «записать эту операцию в журнал»), даже если некоторые узлы падают или сообщения теряются.

### Зачем нужен консенсус

В системах типа Kafka/KRaft, etcd, Hazelcast нужен механизм:
* выбора лидера
* согласования shard maps
* согласования offset checkpoints
* согласования конфигураций

Consensus — это задача согласования одного и того же значения между несколькими узлами в ненадёжной распределённой среде (сбои, задержки, разделение сети).

### Core ideas

* Каждый proposal проходит через процесс запрос/accept/commit.
* Кворум (majority) нужен, чтобы гарантировать пересечение между разными раундами — никто не «потеряет» уже committed данные.
* Жизненный цикл одного решения: propose → replicate → majority ack → commit → apply.

_Почему нужен:_ чтобы избежать split-brain и потерянных записей. Без consensus два лидера могли принять разные коммиты → консистенция нарушена.

### Алгоритмы Consensus

И Paxos, и Raft решают одну и ту же задачу: fault-tolerant replicated state machine через консенсус.

#### 1. Paxos

Семейство алгоритмов для достижения консенсуса. Основная цель: выбрать одно значение, устойчивое к сбоям узлов. Исторически — первая формальная и широко признанная модель.

_Главная идея_
* разделение на proposal / accept / learn
* majority quorum
* большинство всегда перекрывается → гарантия safety

В инженерии Paxos редко нужен: Raft проще.

#### 2. Raft

Альтернативный алгоритм консенсуса, созданный как более понятный аналог Paxos, выполняющий те же цели (лидерство, лог репликации, достижение единого согласованного состояния).

##### a. Log Replication с commit правилами

Лидер определяет порядок записей.
Follower-ы копируют их.
Commit = majority acknowledgement.

##### b. Safety

Если запись committed в term X → ни один будущий лидер не потеряет её.

##### c. Leader election

* randomized timeout
* term как fencing
* лидером может стать только узел с наиболее “длинным” логом

##### d. Reconfiguration

Raft делает joint consensus:
* старая конфигурация + новая
* переход атомарный

Это важно для cluster scaling.

## Quorums

Механизм принятия решения в кластере, где корректность основана на том, что любое решение принимается большинством узлов (или пересекающимися подмножествами узлов).

### Зачем нужны
Чтобы гарантировать единственность решения при сбоях.
Идея: если любое разрешённое множество узлов пересекается с другим, два противоречащих решения не могут быть приняты одновременно.

### Типовые виды

* Read quorum (R)
* Write quorum (W)
* Требование: R + W > N (N — число узлов)

### Использование

* Консенсусные протоколы.
* Распределённые БД: Cassandra, Riak, Dynamo.
* Реплицированные логи и distributed locks.

## Distributed Locks

Способ гарантировать, что только один участник в распределённой системе может выполнить критическую секцию.

_Проблема:_ В нескольких узлах нет общей памяти → невозможно использовать mutex → нужны протоколы координации.

### Основные способы реализации

1. Quorum-based locking<br>
    Клиент получает «большинство» реплик. Если есть majority lock — lock считается взятым.
2. Lease-based lock<br>
   С временным TTL, чтобы избежать deadlock при сбое владельца.
3. CAS / Compare-and-Swap на централизованном сторе (ZooKeeper, etcd, Consul).<br>
   Узел получает «znode» или «key» только при версии X.
   Это безопаснее, чем «set-if-not-exists».

### Основные проблемы

* Потеря lock при pause-the-world (GC).
* Сплит-брейн.
* Старый клиент может думать, что lock ещё его.

Эта проблема решается через fencing tokens (ниже).

## Membership & Heartbeat

Подсистема, определяющая, какие узлы считаются живыми, какие умершими и кто входит в кластер.

### Membership

_Решает:_
* кто в кластере;
* как обрабатывать вступление/выход узлов;
* как распространяются изменения состава.

_Типовые реализации:_
* Gossip-based (Cassandra, Serf).
* Centralized registry (ZooKeeper, etcd).
* Consensus + membership (Raft делает membership changes через консенсус).

### Heartbeat

Периодические сигналы «я жив».

_Используется для:_
* детекции отказов;
* выбора лидера;
* расчёта timeouts.

_Проблемы:_
* сети ненадёжны → невозможно точно определить смерть узла. Только подозрение (suspected crash).
* слишком маленький timeout → ложные подозрения.
* слишком большой → медленное переключение.

## Fencing tokens

Механизм защиты от ситуации «старый клиент всё ещё думает, что lock его», когда lock выдан заново новому клиенту.

_Задача:_ 
Предотвратить «split-brain владельцев ресурса» при lease-based lock.

_Как работает:_
* Каждый раз, когда lock выдаётся, сервер увеличивает монотонный токен, например token = 1,2,3,4....
* Клиент передаёт этот токен дальше (например, хранилищу или файловой системе).
* Сервер ресурса принимает только операции с самым новым токеном. 
* Старые токены → автоматически отклоняются.

_Пример (упрощённо):_
* Клиент A получил lock с токеном 10, потом завис.
* Lock истёк.
* Клиент B получил lock с токеном 11.
* Клиент A «проснулся» и пытается писать. Его токен 10 → отклоняется.

_Гарантия:_ 
Даже если lock по времени истёк, старые клиенты ничего не сломают.
