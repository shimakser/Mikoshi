# Rate Limiting

Это механизм управления внешним или внутренним трафиком, позволяющий ограничить скорость входящих запросов или событий, чтобы защитить систему от перегрузки, DDoS, резких всплесков нагрузки, неравномерных клиентов и предотвратить каскадные отказа.

_Если Backpressure управляет скоростью обработки, то Rate Limiting регулирует скорость приёма запросов._

---

## Основные цели

### Защита от перегрузки

Если поток запросов превышает обработку downstream-слоя, необходимо стабилизировать входящую нагрузку.

### Защита от злоупотреблений

_Ограничение:_
- частоты API вызовов на пользователя/токен/ключ
- частоты создания ресурсов
- brute-force на логине
- спам-операций

### SLA изоляция

Чтобы "плохие клиенты" не ухудшали латентность "хорошим".

### Billing / Fair usage

Если API коммерческий — ограничение на QPS = финансовый контроль.

## Модели: фундаментальные концепции

### Fixed window

_Простое правило:_ “не более X запросов за Y секунд”.

_Недостаток_ — сильный _burst-эффект_ на границах окон:

Клиент может сделать:
- 100 запросов в последнюю секунду окна (в 12:00:59),
- и сразу ещё 100 запросов в следующую секунду нового окна (12:01:00).

Это 200 запросов за 1–2 секунды, хотя лимит — 100 за минуту.

### Sliding window

_Смысл:_ убрать burst-эффект Fixed Window, анализируя не жёсткие минуты, а скользящий интервал времени.

Хранится история запросов; окно "скользит". Вы каждый раз проверяете:
- когда пришли последние N запросов,
- укладываются ли они в 60-секундный диапазон относительно текущего времени.

То есть окно скользит, а не привязано к минутам.

Лучше предсказуемая нагрузка, но дороже в реализации (нужен список меток времени или bin counters).

#### Есть две формы:

- **Sliding Window Log** — храните timestamps всех запросов (дорого).
- **Sliding Window Counter** — экстраполируете count между текущим и предыдущим окном (более дешёвый приближённый вариант).

### Leaky Bucket

Это очередь, из которой элементы (запросы) вытекат **с фиксированной скоростью**, независимо от входного потока.

#### Как работает:
- Есть "ведро" (очередь N фиксированной длины).
- Запросы приходят и помещаются в очередь.
- Из очереди они «вытекают» с фиксированной скоростью, например, 10 rps.
- Если очередь заполнена — новые запросы отбрасываются.

#### Что это даёт:
- Backend получает ровный поток 10 rps.
- Независимо от того, что на входе может быть 1000 rps.

#### Для чего применяется:
- стабилизация нагрузки,
- защита backend от скачков,
- совместимость со строгими SLA по ритму обработки.

#### Отличие от Token Bucket:
- Leaky Bucket сглаживает поток, делая его равномерным.
- Token Bucket разрешает burst-ы, но в ограниченном объёме.

Гарантирует stable throughput, подавляет бурсты.

### Token Bucket

#### Поведение
- Чтобы обработать запрос, нужно 1 токен.
- Если токен есть — он расходуется, запрос разрешён.
- Если нет — запрос отклоняется.
- Токены «капают» со временем до max capacity.

_Преимущество:_
- не только стабилизирует скорость, но позволяет бурсты (пока есть токены).

#### У алгоритма есть параметры:
- `bucket_capacity` — максимальное количество токенов (например, 100).
- `refill_rate` — сколько токенов добавляется в единицу времени (например, 10 токенов в секунду).
- `refill_interval` — периодичность (каждую секунду или непрерывный расчёт через формулу).
- `current_tokens` — состояние.

#### Где хранится состояние (current_tokens)
1. In-memory
   - Nginx (local limit_req zone), Envoy local rate limit, локальные rate limit middleware.
   - обычная переменная в памяти процесса, обновление в момент запроса, никаких внешних зависимостей.
   - _Минус:_ не работает распределённо без синхронизации.
2. Redis
   - ключ в Redis
   - _Обновление:_ атомарный Lua-скрипт (Redis), инкремент/декремент + проверка TTL, вычисление refill — по формуле из времени последнего обновления.
   - Работает кластерно.
3. Внутри самого сервиса
   - _Хранится:_ токены — ConcurrentHashMap<key, state>, время последнего refill, параметры bucket.
   - _Минус:_ не синхронно.

#### Как отслеживаются токены (механика refill)

1. Дискретный refill:

   Каждые X миллисекунд происходит refill:

        current_tokens = min(capacity, current_tokens + refill_rate)

   _Проблемы:_
    - создаёт ступенчатое поведение,
    - нужен scheduler.

2. Непрерывный refill (формула)

   Считается в момент запроса:

        elapsed = now - last_refill_ts
        new_tokens = elapsed * refill_rate
        current_tokens = min(capacity, current_tokens + new_tokens)
        last_refill_ts = now

   _Преимущества:_
    - нет отдельного job,
    - точное соответствие rate,
    - хорошо подходит для Redis (Lua).

### Итоговое сравнение 

| Модель         | Смысл                    | Плюсы                       | Минусы            |
| -------------- | ------------------------ | --------------------------- | ----------------- |
| Fixed Window   | простое окно             | простота                    | burst на границах |
| Sliding Window | окно по времени от *now* | точное ограничение          | дороже            |
| Leaky Bucket   | плавный постоянный выход | стабилизация нагрузки       | нет burst-ов      |
| Token Bucket   | накопление токенов       | burst-ы в разумных пределах | нужно состояние   |

## Где именно ставят Rate Limiting

### На уровне клиента (client-side throttling)

Клиент регулирует количество запросов.

Хорошо для SDK, плохое место для защиты (клиент можно подделать).

### На уровне API Gateway

Оптимальный вариант:
- NGINX / Envoy / Kong / Apigee / AWS API Gateway
- централизованная политика
- распределённое хранение лимитов

Здесь работают миллионы запросов в секунду.

### На уровне сервиса

Используется для отдельных типов операций:
- limit-per-user
- limit-per-resource
- limit-per-action

Но сервис видит трафик только на себя, а не на весь API.

### На уровне базы данных / брокера / очередей

_Пример:_ ограничение Connections-per-user в Postgres.

Это тоже rate limiting, но специфичный.

## Стратегии реакции на превышение лимита

### Hard reject (429 Too Many Requests) — стандартный и рекомендуемый

Система просто отказывает.

### Soft reject

Ограничение:
- замедление (503 + Retry-After)
- "wait until next slot"
- задержки перед обработкой

Рекомендуется для queues/batch.

### Priority-based shedding

Запросы разных типов имеют разный приоритет:
напр., метаданные — низкий приоритет, платежи — высокий.

### Dynamic throttling (адаптивные лимиты)

Например:
- если latency растёт → автоматически урезаем пропускную способность
- если DB CPU > 80% → уменьшаем RPS upstream

## Типовые ошибки при реализации

### Неограниченные local counters

Клиент обходит лимит через много инстансов.

### Задержки времени и проблемы со скользящими окнами

Часы на разных инстансах → inconsistency.
Лучше хранить timestamps на сервере ограничений.

### Использование NGINX limit_req с недостаточной настройкой burst

Может резать слишком много.

### Слишком большой TTL для counters

Counters растут → память расходуется.

### Ошибки в кэшах (особенно при слабой консистентности)

Например:
- клиент шлёт 1000 RPS
- кэш TTL = 1s
- один инстанс считает 1000, другой считает 1000 → итог 2000 RPS вместо 1000

## Метрики для Rate Limiting

### На Gateway
- Allowed RPS
- Throttled RPS
- Rejected (429)
- Latency до rate limiter backend (Redis)
- Saturation времени выполнения Lua-скриптов

### На приложении
- retries
- drop rate
- priority distribution

### На кластере Redis
- memory footprint
- CPU
- hotspots

## Интеграция Rate Limiting c другими механизмами

### Backpressure

- Rate limiting останавливает нагрузку до входа в систему.
- Backpressure управляет внутренним выполнением.

Они взаимодополняемы.

### Circuit Breakers

- Если downstream перегружен → rate limiting upstream.
- Если upstream ломает downstream → CB блокирует upstream.

### Load Shedding

- Лимиты — это механизм отбора.
- Load shedding — политика, по каким критериям резать нагрузку.

## Best practices | правила внедрения

### Чётко определить “key” для ограничения

Что лимитировать:
- по IP,
- по user_id,
- по API key,
- по endpoint,
- по комбинации user_id + endpoint,
- по client type (mobile/web),
- по tenant.

_Правило:_ один rate limit всегда привязан к конкретному ключу, иначе метрика размывается.

### Решить, что мы ограничиваем: RPS, burst, или скорость потребления

_Типы ограничений:_
- hard RPS (строгий максимум, без всплесков),
- burst RPS (нужен Token Bucket),
- плавное сглаживание (нужен Leaky Bucket),
- rate per time window (нужны Sliding Window).

_Вопросы, которые нужно уточнить:_
- допускаются ли всплески?
- нужна ли равномерная нагрузка?
- нужна ли защита backend?
- важнее доступность или строгость лимита?

### Выбрать алгоритм, исходя из SLA и поведения системы

* Если нужны bursts — Token Bucket.
* Если нужен ровный поток — Leaky Bucket.
* Если нужна точная статистика без пиков — Sliding Window Log.
* Если нужна простота — Fixed Window.

### Определить уровень применения

Уровни:

1. На API Gateway (Nginx, Envoy, Kong)
   - лучший вариант для защиты сервиса до его попадания внутрь,
   - дешевле и быстрее,
2. На уровне сервиса (middleware)
    - если нужна бизнес-логика: «5 покупок в час», «3 попытки login в минуту»,
    - но плохо подходит для защиты от нагрузки.
3. В базе / кеш-слое (Redis global limit)
    - для распределённого rate limit между всеми инстансами,
    - атомарность через Lua.

Правило: если приложение распределённое — нужен внешний state (Redis).

---

## Итог

Начинаем с определения ключа ограничения и типа лимита (burst или строгий RPS).
Затем выбираем алгоритм: Token Bucket для bursts или Leaky Bucket для сглаживания.
Далее выбираем уровень применения: обычно Rate Limiting ставится в API Gateway и строится на Redis с атомарными Lua-скриптами.
Обязательно храним состояние токенов централизованно, делаем корректный refill, настраиваем HTTP 429 с Retry-After, разделяем лимиты по классам клиентов, добавляем наблюдаемость и тестируем нагрузкой.
Особое внимание уделяем обходу лимитов и поведению при падении Redis (fail-open / fail-closed).
