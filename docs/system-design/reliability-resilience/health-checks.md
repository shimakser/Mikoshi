# Health Checks

Это механизм проверки состояния компонента системы: сервиса, базы, брокера, ноды кластера, контейнера.

_Цели:_
- своевременно обнаружить деградацию или отказ;
- дать балансировщикам и оркестраторам сигнал о том, как обращаться с инстансом;
- включить или исключить узел из кластерной топологии;
- триггерить авто-рескейлинг, эвакуацию нагрузки или перезапуск.

Health Check ≠ Monitoring
Health Check — бинарно (здоров/не здоров), Monitoring — метрики, которые позволяют оценивать тренды и производительность.

---

## Основные типы

### Liveness Check

_Цель:_ понять, что процесс жив, а не завис в deadlock, бесконечном GC, dead-loop и т.д.

_Обычно:_
- проверяет минимальный функционал (например, что поток обработки жив, event loop отвечает);
- не должен проверять внешние зависимости (так как они могут быть временно недоступны);
- если liveness = unhealthy → контейнер перезапускают.

_Примеры:_
- Kubernetes: /livez
- Spring Boot: actuator/health/liveness

_Важно:_ Liveness должен быть максимально дешёвым и локальным.

### Readiness Check

_Цель:_ понять, что сервис готов обслуживать трафик.

_Признаки:_
- загружены конфиги,
- прогрет кэш,
- установлены соединения с БД,
- миграции применены,
- служба может обрабатывать реальные запросы.

Если readiness = unhealthy → сервис живой, но не должен получать трафик.

_Примеры:_
- Kubernetes: /readyz
- Spring Boot: actuator/health/readiness

### Startup Check

_Цель:_ понять, что сервис успешно прошёл инициализацию и может перейти к обычным liveness/readiness.

_Пример:_
- Kubernetes: /startupz

### Dependency Health Checks

Сервис может быть живым, но зависимость умерла или работает нестабильно.

Проверяются:
- БД,
- очередь сообщений,
- кэш,
- внешний API.

_Важно:_ проверки зависимостей никогда не должны ломать liveness, иначе перезапуск начнётся из-за внешней проблемы → каскадный отказ.

---

## Почему Health Checks нужны в распределённой системе

1. Traffic Steering.<br>
   Если readiness = false:
    - узел исключается из пулов,
    - на него не идёт трафик,
    - он может выполнять recover (warm-up, sync, migration).
2. Failover.<br>
   При деградации ноды кластер должен:
    - выбрать новый лидер,
    - перевести shard в другой реплике,
    - остановить обработку на умирающем узле.
3. Auto-scaling.<br>
   HPA/KEDA/Kubernetes или другая система может использовать health info, чтобы:
   - поднять новую ноду,
   - удалить старую,
   - перезапустить зависшую.
4. Distributed Coordination.<br>
   Системы вроде etcd/ZK/Kafka должны знать «жив» узел или нет.

## Примеры Health Checks в реальных системах

### Kubernetes

#### Liveness Probe

Проверяет основную функциональность:
- HTTP GET,
- exec,
- TCP socket.

#### Readiness Probe

Если unhealthy → Endpoint удаляется из Service → трафик перестаёт идти.

#### Startup Probe

Помогает «тяжёлым» приложениям, которые долго прогреваются:
- Startup проходит → включаются liveness/readiness
- Startup не проходит → контейнер перезапускается

### Spring Boot Actuator

#### Health indicators

* Disk space
* Database connectivity
* Redis
* Kafka
* JMS
* Custom indicators

#### Groups

* liveness
* readiness

## Как внедрять Health Checks

1. Разделить health endpoints.
   - /health/live — только internal status.
   - /health/ready — включает зависимости.
2. Определить критерии готовности.
3. Ввести уровни статуса.
4. Включить узел в orkestrator/lb через readiness only.<br>
   LB не должен слать трафик на «живой, но не готовый» инстанс.
