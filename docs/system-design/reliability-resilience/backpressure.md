# Backpressure

**Backpressure** — это механизм управления скоростью входящего потока, гарантирующий, что нагрузка никогда не превышает реальную пропускную способность downstream-компонентов.

_Другими словами:_ когда система “не успевает”, она должна заставить источники трафика замедлиться или отказаться принимать новые запросы.

_Это фундамент для устойчивости:_ поток должен быть ограничен с учётом пропускной способности downstream-компонентов.

---

## Почему backpressure важен

Без него система умирает по механике:


    очередь растёт → задержки растут → таймауты → retry-шторм → death spiral.

---

## Архитектурная роль

Перегрузкой может быть:
- недостаток CPU
- переполнение очередей (bounded queues)
- медленный downstream (БД, API, сервис)
- нехватка соединений в пуле
- GC-паузы
- ограничение throughput(пропускной способности) по диску
- медленный network link

Backpressure — это системная безопасность: не допустить превышения лимитов. 

---

## Подходы к реализации

### Push-based система

Producer активно шлёт данные consumer-у.
Backpressure делается через “замедление” producer-а.

### Pull-based система

Consumer сам запрашивает данные с нужной скоростью.
Backpressure встроен в саму модель: нет запроса → нет нагрузки.

---

## Механизмы

### Queue-based backpressure

Возникает, когда очередь достигает лимита, и система должна принять решение, что делать дальше.

При достижении лимитов очередей:
- отказ во входящих запросах (HTTP 429/503).
- Dropping strategies
  - drop oldest — удаляем старые элементы → актуальность сохраняется.
  - drop newest — не принимаем новые сообщения, сохраняем историю.
  - drop tail (в Streams) — отбрасываем последние элементы очереди — часто в сетевых буферах.
  - sample & throttle — только часть элементов допускается к обработке.
- pause/resume каналов.

### Producer-driven backpressure

Если потребитель не успевает, то источник нагрузки должен замедлиться.

Producer снижает скорость при заполнении буфера:
- TCP: window size, congestion control
- Kafka: max.in.flight.requests, linger.ms, batch size
- Reactive Streams: request(n)

### Adaptive backpressure

Скорость регулируется динамически:
- Exponential delay / increase
- Token bucket feedback
- Latency-aware throttling

### Сравнение подходов

| Механизм            | Основная идея                              | Где эффективен                       | Сложность |
| ------------------- | ------------------------------------------ | ------------------------------------ | --------- |
| **Queue-based**     | ограничение входящей очереди → reject/drop | микросервисы, API, thread pools      | низкая    |
| **Producer-driven** | источник замедляется автоматически         | Kafka, TCP, streaming systems        | средняя   |
| **Adaptive**        | динамическое управление rate               | high-load API, distributed pipelines | высокая   |

## Механизмы по уровням системы

### Transport-level Backpressure (сетевой уровень)

#### TCP windowing

_TCP автоматически регулирует скорость:_ если принимающая сторона медленная → уменьшается TCP receive window → sender замедляется.

Это “низкоуровневый” backpressure. Он работает всегда.

Но он не знает бизнес-логики, поэтому:
- может быть слишком медленным
- может приводить к росту очередей в приложении, если приложение не читает быстро

#### HTTP/2 flow control

Есть window updates для streams.
Consumer уменьшает окно → producer не может отправлять больше данных.

### Application-level Backpressure

#### Bounded queues

Если очередь достигла лимита:
- drop (с разными стратегиям)
- reject
- block
- shed load

Всё зависит от критичности сервиса.

#### Thread pool saturation backpressure

_Суть:_ если thread pool насыщен — мы должны не принимать новые задачи, а не складывать их в бесконечную очередь.

_Причина:_ бесконечная очередь = бесконечная задержка → таймауты → ретраи → деградация.

Правильные политики:
- CallerRuns + bounded queue
- AbortPolicy
- Load shedding (даже лучше)

#### API-side backpressure (HTTP 429, 503)

Сервис может выдавать:
- 429 Too Many Requests
- 503 Service Unavailable

Это официальный способ сообщить клиенту: “я не тяну”.

### Distributed-system-level Backpressure

#### Kafka

Backpressure происходит так:
- producer видит, что broker медленный → send buffer заполняется → linger & batch → замедление → ошибки TimeoutException
- consumer сам регулирует скорость обработки → commit offset только после обработки → не забирает больше данных, чем может обработать

Kafka естественным образом предлагает backpressure в обе стороны.

#### gRPC streaming

Есть встроенный механизм **request(n)** — Consumer сам говорит, сколько сообщений он готов принять.

### Reactive Backpressure (Reactive Streams / Project Reactor / Akka Streams)

#### request(n)

_Суть:_ consumer говорит, сколько элементов он готов обработать.
producer обязан уважать этот лимит.

Producer должен:
- не выпускать больше n элементов, пока не придёт новый request();
- уважать backpressure даже если он «может» производить быстрее.

#### Strategies при ограничениях

- buffer (bounded/unbounded) — Producer складывает элементы в буфер.
- drop / dropLatest / dropOldest — Когда буфер заполнен, элементы отбрасываются.
- error.
- latest — отдавать только последний элемент.

## Алгоритмы и стратегии

### Reject Early vs Queue Late

#### Reject Early (правильно для большинства)

Не принимаем запросы при перегрузке:
- минимальная задержка
- легко предсказуемо
- отсутствие cascaded failures

#### Queue Late (опасно)

Принимаем запрос, кладём в очередь → растущая очередь убивает систему.

#### Почему "Reject Early" — золотой стандарт

Потому что SLA определяется latency, а не количеством обработанных запросов.

### Token-based Backpressure

Producer получает токены от consumer-а:
- больше токенов → выше скорость
- нет токенов → блокировка/ожидание

### Credit-based backpressure (используется в сетевых протоколах)

Consumer сообщает producer-у количество доступных слотов/байтов.
Producer ограничивает передачу этим количеством.

Это даёт строгий контроль скорости.

## Ошибки при отсутствии Backpressure

### Retry storm

Если сервис падает по таймаутам, клиенты начинают ретраить.
Это усиливает нагрузку → полный outage.

Backpressure предотвращает этот сценарий.

### Cascading failures

Если один сервис перегружен, его соседи тоже падают.

### Memory blowup

Неограниченные очереди → out-of-memory.

## Метрики, по которым видно перегрузку

- Queue depth
- Time-in-queue
- Active threads vs максимальное число
- Latency p99/p999
- Drop rate
- Retries
- Timeouts
- GC pauses
- Syn backlog

### Что такое p99

**p99 latency** — это перцентиль, показывающий время обработки, которое хуже, чем у 99% всех запросов, и лучше только у 1% самых медленных.

То есть если p99 = 250 мс, значит:
- 99% всех запросов завершаются быстрее 250 мс,
- 1% запросов — медленнее.

## Архитектурные паттерны

### Load Shedding

Целенаправленный отказ от части запросов.

### Queue limits (strict)

Стратегия: лимиты должны быть жёсткими.

### Circuit Breaker

Отказывает в запросах при перегрузке downstream-а.

### Bulkheads

Архитектурный приём, который жёстко изолирует части системы друг от друга, чтобы сбой или перегрузка в одном компоненте не потянули за собой весь сервис.

Т.е. один перегруженный поток не убивает всё.

## Best practices | правила внедрения

### Порядок внедрения Backpressure

1. Измерить throughput и latency. 
2. Найти bottleneck. 
3. Понять, какой элемент перегружен (CPU, DB, I/O, network). 
4. Ввести жёсткие лимиты очередей. 
5. Ввести отказ входящих запросов при перегрузке. 
6. Ввести circuit breaker. 
7. Настроить retry policy (джиттер, экспонента). 
8. Если нужно — включить адаптивное throttling. 
9. Добавить метрики. 
10. Тестировать fault injection-ом.

### Чётко определить, где именно возникает давление

Backpressure нужен, только если bottleneck может возникнуть:
* между producer → broker,
* между broker → consumer,
* внутри сервиса (между этапами pipeline),
* между сетевым слоем и обработчиком,
* между CPU и диском.

Первый шаг: найти конкретный участок, где пропускная способность меньше, чем входной поток.

### Определить модель взаимодействия: push vs pull

_Основание:_ модель подсистем Kafka/RxJava/Reactive Streams.

* Если система push-based → требуется механизм “signal backpressure upstream”.
* Если pull-based → ограничение потребителя является естественным backpressure.

_Правило:_ в ideal-case всю систему строить в pull-стиле (consumer-driven).

### Определить поведение при достижении предельной нагрузки

Что будет происходить, если сервис не может принимать больше данных:
* замедлить отправителя,
* остановить отправителя,
* отбросить сообщения,
* буферизовать (bounded buffer),
* маршрутизировать в другую очередь,
* деградировать функциональность.

Выбирается исходя из критичности данных.

### Принять явное решение: что делать с входящими запросами при давлении

_Опции:_
* Drop (fail-fast) — если SLA важнее, чем доставка.
* Retry c экспоненциальной задержкой — если данные важны, но можно ждать.
* Повышать latency отправителя — классический вариант pull-модели.
* Отключить приём на время (circuit breaker)— если проблема — временная деградация.
* Отправить в другую очередь / DLQ — если есть алгоритм последующей обработки.

### Учесть политику повторных попыток

Retry без backpressure равен DDoS собственному сервису.

_Правило:_
* использовать exponential backoff,
* добавлять jitter (случайное смещение),
* ограничивать максимальное число попыток.

---

## Итог

Начинаем с поиска bottleneck и определения push/pull модели. Затем выбираем bounded очереди и определяем механизм распространения сигнала backpressure вверх по цепочке — через протокол, фреймворк или через внешний storage типа Kafka/RabbitMQ.
Далее определяем политику поведения при перегрузке: drop, throttle, retry или route to DLQ. Обязательно включаем метрики: глубина очередей, пропускная способность, latency, число отказов.
Backpressure синхронизируем с autoscaling, настраиваем ограниченные буферы, добавляю jitter для retry и проектируем систему так, чтобы она оставалась предсказуемой при росте нагрузки.
Основная цель — сделать так, чтобы система не "умирала тихо", а явно сообщала upstream, что нужно сбавлять скорость.
