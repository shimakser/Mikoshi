# Observability: Metrics, Logs, Tracing

**Observability** — способность системы раскрывать своё внутреннее состояние через внешние сигналы.

Основа: три типа сигналов.
1. **Metrics** — числовые агрегаты состояния и производительности.
2. **Logs** — детальные события и контекст.
3. **Tracing** — сквозные цепочки вызовов между сервисами.

_Применяются вместе:_ каждая категория не заменяет другие.

* Metrics → сигнализируют, что что-то пошло не так.
* Tracing → показывает, где именно.
* Logs → объясняют, почему.

---

## Определения

* **SLI** — что измеряем.
* **SLO** — какого уровня качества хотим достичь.
* **SLA** — юридические обязательства.

## Metrics

_Цель:_ дать количественное, агрегируемое представление о состоянии системы.
Это наиболее дешёвый по объёму сигнал и основной для alerting.

### Какие бывают

Стандартная модель (Prometheus/OpenTelemetry):

1. Counter.<br>
   Только растёт.<br>
   Использование: количество запросов, количество ошибок, количество сбросов кеша.
2. Gauge.<br>
   Может расти/падать..<br>
   Использование: активные соединения, размер очереди, heap usage.
3. Histogram / Summary.<br>
   Измерение распределений времени / размера..<br>
   Использование: latency, payload size.

### Основные метрики

1. RED-модель (для API)
    - Rate — запросы в секунду
    - Errors — количество ошибок в секунду
    - Duration — распределение задержек (histogram)
2. USE-модель (для ресурсов)
    - Utilization — сколько ресурсов используется (% CPU, pool usage)
    - Saturation — насколько ресурс перегружен (очереди)
    - Errors — сбои ресурса

## Logs

_Цель:_ дать детальный контекст о том, что произошло.

_Метрики показывают что, а логи объясняют почему._

### Принципы

1. Structured logs, не текстовые строки.<br>
   Формат JSON. Причина: удобный парсинг, объединение, поиск.
2. Корреляционные идентификаторы обязательны
   - trace_id
   - span_id
   - request_id
   Без них — невозможно понять, к какому запросу относится лог.
3. Уровни логирования
    - ERROR — лишь ошибки, которые требуют внимания
    - WARN — ситуации риска
    - INFO — ключевые операции (start/stop job, внешние вызовы)
    - DEBUG — подробности (должны быть отключены по умолчанию)

### Что обязательно логировать

* входящие запросы (метаданные + статус)
* исходящие запросы
* retry / таймауты
* circuit breaker open/close
* security-события
* критические ошибки

## Tracing

Tracing = понимание полного пути запроса по системе.

- Trace — полный путь запроса.
- Span — одна операция внутри сервиса.

Корреляционные идентификаторы:
- trace_id
- span_id
- request_id

## Как строится


### Основные инструменты

* Prometheus (metrics pull)
* Grafana (дешёвые дашборды)
* Alertmanager (алерты по SLO)
* ELK / OpenSearch / ClickHouse (логи)
* Jaeger / Tempo / Zipkin (tracing)
* OpenTelemetry — единый SDK для всего

### Обязательные элементы архитектуры

* Обязательные элементы архитектуры
* единый trace_id везде
* единый log format
* центральное место для хранения метрик и логов
* дашборды по сервисам
* алерты, основанные на SLO, а не на raw метриках
