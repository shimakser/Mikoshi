# GraalVM

GraalVM — это альтернативная виртуальная машина для экосистемы Java, в которую входит:
1. Graal JIT-compiler<br>
    Более продвинутый JIT, заменяющий HotSpot C2. 
2. Native Image<br>
   Инструмент AOT-компиляции Java-приложений в статически слинкованный исполняемый файл.

_Поддержка языков:_ Java, Kotlin, Scala, JavaScript, Python (ограниченно), Ruby, LLVM IR.

### Быстрый старт

Native Image стартует в миллисекундах, потому что:
* нет полного JVM bootstrap
* нет прогрева JIT
* нет загрузки classloader-иерархии

_Это важно для:_
* Serverless (AWS Lambda, GCP Functions)
* CLI-утилит
* Kubernetes autoscaling (быстрые pod startup)

### Очень маленький runtime footprint

JVM → сотни МБ (full JRE).<br>
Native Image → десятки МБ.

_Полезно для:_
* маленьких контейнеров
* edge/FaaS
* ограниченных сред

### Predictable performance

JIT может резко «подпрыгивать»:
* warmup
* recompile
* deopt

Native — фиксированный AOT-код, предсказуемый.

---

## Native Image

Это AOT (Ahead-Of-Time) компилятор:<br>
Java-код → анализ → выделение reachable кода → создание бинарника → запуск без JVM.

_Бинарник содержит:_
* статически собранный heap (image heap)
* минимальную runtime-библиотеку Substrate VM
* машинный код

---

## Чем GraalVM и Native Image хороши

### Startup time: лучший в Java-экосистеме

В реальности:
* JVM: сотни миллисекунд – секунды
* Native Image: 5–30 мс

### Память

* JVM RSS: 150–300 МБ
* Native Image: 20–80 МБ

### Single binary

Нет зависимости от JDK/JRE.<br>
На практике хорошо для DevOps.

### Отличный JIT (если не Native)

Если использовать Graal JIT вместо C2:
* быстрее на некоторых workloads
* лучше оптимизирует большие горячие функции
* поддерживает aggressive inlining

### Безопасность

Меньшая поверхность атаки: меньше runtime компонентов.

---

## Минусы Native Image

### Медленный и тяжёлый билд

Native Image компилируется минуты, иногда десятки минут.<br>
_Причина:_ статический анализ, tree-shaking, linking.

### Хуже производительность на длительных нагрузках

JIT оптимизирует код во время работы → выигрывает на long-running сервисах.
Native AOT — статический код → хуже оптимизации.

Если сервис:
* живёт долго
* имеет стабильно горячие участки

→ классическая JVM часто быстрее.

### Ограничения reflection, динамики

Из-за полного AOT-анализа:
* reflection требует ручной регистрации классов
* динамические прокси требуют регистраций
* serialization тоже
* dynamic classloading невозможен

Это ключевая проблема для Spring, Hibernate, Jackson (частично решена GraalVM-friendly фреймворками, но остаётся сложностью).

### Ограниченные профили оптимизации

Native AOT = компиляция вслепую.<br>
JIT видит реальную нагрузку → оптимизирует точнее.

### Size может быть всё равно большим

20–80 МБ для маленького приложения многовато для некоторых use-case.

### Debug/diagnostics хуже

JVM даёт:
* JFR
* JMX
* профилирование
* heap dump

Native не даёт столько инструментов. Часть есть, но намного хуже.
